## 0. Verdict in five lines

1. The diagnosis's reading of the emulator is right, with one refinement: the old engine answers most deaths after the card,
   but already answers five of them inside the hit, so the migration changes the order of *some* deaths, not all (section 1).
2. The kernel's kill (`Core2/Commands/CreatureCmd.Kill.cs`) is in the game's shape and well tested in isolation. What is not
   tested anywhere is the path the agent actually takes: an old-engine step, with the switch on, through a real card, a real
   kill, a real death handler and a mid-card screen. R4 (the reroute) is where the risk lives and no test crosses it yet.
3. The port list covers the death *bodies*; it misses three old-engine *index* dependencies that a mid-card removal breaks
   (section 1.3) and one enemy-turn bookkeeping hazard the plan's IsPerformingMove bullet does not reach (section 1.3, item C).
4. The proof plan proves structure and no-switch identity; with the switch on its only game-side oracle is the lockstep
   re-measure after landing. Two cheap oracles exist already and are not in the acceptance list: the traced set with net states,
   and the old engine's own behaviour suites run under the switch (section 2.3).
5. The cloud handler pattern is sound for value folds and unsound as written for one class of event handler: an old body that
   acts on every holder, dispatched once per holder. Ravenous, the first batch's own model, is the case (section 3.3).

## 1. The mechanism

### 1.1 Is the diagnosis's reading consistent with the code? Yes, with precision added

One repetition of a play (`CombatEngine.ResolvePlayRepetition`, CombatEngine.cs:814) runs the card's effect
(`CardEffects.Apply`, near line 953), then `HandleEnemyDeaths` (near line 963, positional against `enemyHpsBefore`), then the after-play
bodies, then `AnswerDeathsSince` (line 1118, by reference against a `Baseline`). Both death checks call `AnswerDeaths`
(line 4552): the death bodies per fallen creature, then the corpse sweep `CombatState.RemoveDepartedEnemies` (line 4699).
A selection a card opens inside its effect (`OpenCardSelection` -> `AwaitSelection`, lines 285-349) throws `HookChoicePending`
when the step has no answer yet; the step catches it (line 113), keeps `PendingSelection` open and returns. So at a Headbutt
screen neither death check has run: the corpse is in `state.Enemies` at 0 HP with its powers, and the survivor has no Ravenous
Strength. That is exactly the G2891c25e0d shape, and the migration plan's section 1 says it was traced on the game side.

Two refinements the diagnosis does not make:

- **Not every death is late.** Inside the hit, `CardEffects.LandDamageOnEnemy` (line 5402) already calls `OnEnemyDeath`
  (line 5622) for a powered hit, which runs `AnswerDeathsHoldingTheFightOpen` (CombatEngine.cs:4830): the five powers of
  `HoldsTheFightOpen` (Steam Eruption, Adaptable, Surprise, Infested, Stock) have their whole death answered and swept inside
  the blow, and Shrink's applier removal (`RemoveDeathBoundPowers`, line 5613) runs on every kill route. So the migration moves
  the order of the *other* death bodies (Ravenous, Gremlin Horn, Hex, Dampen, Possess, Heist, Swipe, Constrict, Crab Rage,
  Melancholy, the Queen's enrage, the Illusion / Reattach / Test Subject revives) and of the roster removal; the five holders
  only move from "powered hits" to "every route", and their unpowered-kill cases (poison, Doom, a bomb) are the ones that change.
- **The old engine's death answer is exclusive where the game's is not.** `AnswerDeaths`'s revive chain `continue`s past
  Infested, Heist, Swipe, Constrict, Melancholy, Ravenous and Steam Eruption for a creature that revived (Illusion, Axebot,
  segment, Test Subject). In the game every AfterDeath listener runs for every death (plan section 3 item 5, step 8). The
  kernel's `Hooks.AfterDeath` pass fixes this by construction once the handlers exist; nothing in the port list names it, so
  it will appear in the fuzzer as an unexplained difference the first time an Illusion dies next to a Ravenous slug.

### 1.3 The misses, in detail

**A. Positional death pairing must be switched off whole.** `HandleEnemyDeaths` compares `enemyHpsBefore[i]` with
`state.Enemies[i]`. After the kernel removes slot 0 inside the card, a corpse that stays (a Reattach segment, an Illusion, the
Test Subject) and shifts into a slot whose creature was alive before is "newly dead" by position, and `AnswerDeaths` would answer
it a second time (a second Gremlin Horn draw). The plan says the old sweep "does nothing under the switch for a death the kill
answered"; the condition must be "under the switch, at all". `AnswerDeathsSince` is safer (by reference, and it skips
`Reviving`), but the same rule applies.

**B. The next effect's target.** `FirstEnemy` returns `state.Enemies[TargetEnemyIndex]` when that creature is targetable, else
the first targetable one. Today a target killed mid-card is still in its slot at 0 HP, so the fallback picks the first living
enemy; the game's `CardModel.CurrentTarget` keeps the dead creature and the attack hits nobody (the engine's own note at
CombatEngine.cs:6731-6735, difference C5-F15). Under the switch the slot is gone, and the int index names the creature that
moved into it: with a roster [A, B, C] and target index 1, a kill of B sends the card's next targeted effect to C, where today it
goes to A and the game sends it nowhere. Any card that resolves its target more than once (`DealDamage` resolves it on each call;
every multi-step effect that calls `FirstEnemy` again) is exposed, and `RollAutoPlayTarget` / `PlayTarget.At` carry the same int.
This is a concrete candidate for the diagnosis's open mechanism F ("one enemy differs by a whole hit"), and it changes *which*
wrong creature is hit, so the lockstep weight could move rather than fall. Remedy: under the switch, resolve the play's target by
reference for the length of the play (`PlayTarget` already is one; `FirstEnemy` should read it, and answer null for a dead or
removed target as the game does), and leave the fallback to the off-switch path.

**C. Death answered inside an enemy's own move.** R4 wraps `EnemyAI.ExecuteIntent` in `CreatureCmd.PerformMove`, so a Waterfall
Giant killed by the player's Thorns during its STOMP (Thorns -> `DealUnpoweredDamageToEnemy` -> the gated `CreatureCmd.Damage`
-> `Kill` -> the Steam Eruption AfterDeath handler -> `TriggerAboutToBlow`, which sets `MoveIndex` to 1000) returns into
`ExecuteIntent`, whose end does `enemy.MoveIndex++` (EnemyAI.cs:889): `IsExploding` is `MoveIndex >= 1001`, so the giant
explodes the next phase instead of standing a phase on ABOUT_TO_BLOW. The old engine avoids this by answering after the loop,
and the engine's own comment at CardEffects.cs:5589-5593 says the in-blow answer was kept off the Thorns path for exactly this
reason. The game's `SetMoveImmediate(forceTransition: true)` survives its move's end; the old move body has no such notion. The
same applies to Ritual, the Vigor refund and `RestoreTemporaryEnemyStrength` on a creature that died and revived in-move, and to
a Test Subject respawn set during its own move. `WaterfallGiantTests.KilledByThornsOnItsOwnTurnItBlowsARoundLater` pins the
right timing and would fail under the switch; the plan's IsPerformingMove bullet covers the room and roster removal only.

**D. The Fogmog fight under the game's primary rule.** `OldCreatures.IsPrimaryEnemy` (OldState.cs:1015) is MinionPower-only, as
the plan says the game is; the old `IsPrimaryEnemy` (CombatEngine.cs:5000) also excludes Illusion, and
`IllusionAndMinionTests.KillingTheLastPrimaryWinsWithAnIllusionStillAlive` pins that the fight is won with an Eye With Teeth
alive. Under the switch `CombatEnd.IsEnding` finds a living primary (the eye, which revives for ever) and the fight cannot end,
unless something kills the illusions on the Fogmog's death. The port list has no Fogmog row and no Illusion row that does it, so
the open-pair gate passes with this fight unwinnable. R3b lists it as a known difference without a closer. It needs a reading
(which override of Fogmog or IllusionPower ends the illusions when their source dies) before switch-on; it is an Act 1 fight.

**E. The agent's reward.** `KillWithoutCheckingWinCondition` step 2 sets a teammate's HP to 0 when the leader's death kills its
minions; `Baseline.Reward` then counts that HP as dealt. The old engine leaves minions standing at full HP. Not a fidelity
question, but the shaped reward is the agent's training signal and it changes on every fight with Minion teammates.

## 2. The design: where the two paths can disagree, and whether the proof plan is enough

### 2.1 Seams of the hybrid

1. **Two "ending" predicates.** The guarded listener iterator reads `CombatEngine.IsOverOrEnding` (Listeners.cs:105) and so does
   `AttackCmd.Execute`; the queue, the win check and `LoseCombat` read `CombatEnd.IsEnding` over `KernelState.Progress`. They
   differ wherever `HoldsTheFightOpen` differs from the registered `ShouldStopCombatFromEnding` handlers (none until power-2/3/4
   and the LOCAL Adaptable and Steam Eruption land) and on the Illusion rule. In that window a Gremlin Merc's death can end the
   fight at the executor's boundary while the hook passes still run as if it were open, or the reverse. R4 reroutes
   `IsOverOrEnding`; nothing asserts the two agree.
2. **Dropped bodies are silent.** With the switch on and a pair unported, the dispatcher finds no handler and does nothing; the
   NotModelled report (`OldListeners.Report`) is advisory. Until the open-pair gate is 0, every fuzzer difference in a death
   field can be either an intended order change or a missing handler, and the signature cannot tell them apart.
3. **Re-entry.** A handler calls an old body (Thorns, Flame Barrier, Surprise's spawn, Stock's respawn); the body calls old
   damage or HP functions; R4 gates those into Core2's commands, so the kernel re-enters itself inside a pass. The game's
   listeners sometimes enqueue instead of awaiting; `construct pauses` for F08 is LOCAL and not built, so no check yet says which.
4. **Marks nobody can detect missing**: `Flying` (the card in flight is in no pile) and `MarkDying` (a dead enemy in the roster
   looks the same before and after its removal). TIER1 section 3 says so; only the kill site's own test guards `MarkDying`, and
   no test yet plays a card whose model has an F08/F10 override while it is in flight.
5. **Index holders across the removal** (section 1.3 A, B): the old step's own positional state outlives the roster change.
6. **The replay of a stopped step.** A screen that opens after the kernel removed a corpse stops the step; the answer replays the
   step from `Before` with the kernel state copied (`KernelState.CopyTo`). Inside one process this is consistent. A document of a
   stopped step (`CombatSnapshot`, `CheckStoppedStep`) written under the switch and read without it, or the reverse, cannot
   replay to the recorded screen; the reader must bind the same switches.
7. **The agent does not see any of it yet.** The native run API refuses a switched-on kernel, so the lockstep re-measure (EmuDump,
   `--engine core2`) will show the gain while self-play keeps running the old order.

### 2.2 What the proof plan proves

- Byte proof, `corpus.py identity`, `sites check`, `gen_hooks --check`, `construct shape`: the gating is inert with no switch
  and the generated code matches the descriptor. Necessary; says nothing about the switched-on order.
- `construct commands`: Core2's call sequence equals the game method's, and no HP/block write escapes the gate. This is the one
  check that would catch a kill step in the wrong place *inside a command*, and it is good. It does not cover the old sites'
  calls into the commands (the 42 + 33 + 19 + 7 callers), only their HP writes.
- K2's listener order against `game_order_key`: membership and order within a pass; it cannot see a pass that fires at the
  wrong moment.
- The kernel's unit tests (`KillCommandTests` 21, `DamageCommandTests` 16, `DamageCounterTests` 15, `CombatEndTests` 8,
  `ActionQueueTests`): the commands in isolation, with test-only handlers. `HeadbuttsCorpseIsGoneBeforeTheCardsNextEffect` calls
  `CreatureCmd.Damage` directly with a synthetic Ravenous; `ADeadEnemyLeavesTheCombatBeforeAHookActionsScreenOpens` removes the
  enemy by hand in a fake host; the whole-run test (`FinishCombatRunsOncePerCombat...`) runs with an empty handler list before any
  reroute, so it is identical to the old engine by construction. None crosses R4.
- The fuzzer (K6): old against core2 by state hash, with `power` setup items. It has no game-side oracle: with the empty handler
  set every death body is a difference; after all batches, every intended order change is a difference. `fuzz_explained.json`
  matches on a signature of up to six field names (`fnmatch`), so a wrong order in the same fields as an explained change is
  accepted silently. It is a regression net between two emulator builds, not a proof of the game's order.
- `struct_compare` on corpus fights: the corpus snapshots are per decision, so they cannot see the inside of a card; the
  G2891 shape itself (a screen mid-card) is visible only where the record has a decision at the screen.

**Enough to accept the migration? Not as listed.** It would accept a kill that runs at the right place in `CreatureCmd.Damage`
and still lands wrong through 1.3 B or C, or through a silent handler gap, because nothing in the list compares the switched-on
step against the game's own order before R7's lockstep re-measure.

### 2.3 Checks that would catch a wrong order (specific)

1. **The traced set, net shape, with the switch on.** COMPARER.md leaves "Core2 on the traced set" for the next round. The 77
   traced first fights carry the game's `NetFullCombatState` at every checksum, which is the only offline record of the roster
   *inside* an action. `struct_calibrate traced --engine core2` with F08+F10 on, gated on "no fight worse than old against the
   game, and the fights whose first difference is a listed corpse improve", is the strongest game-side check available without a
   PC and should be in section 6's acceptance, ahead of the corpus run.
2. **A step-API acceptance test from the traced Headbutt fight** (section 3.2): the one case whose expected values are a game
   trace, not an inference.
3. **The old behaviour suites under the switch.** `DeathCheckTests` (26), `CombatEndingGateTests` (31), `CorpseRemovalTests`,
   `WaterfallGiantTests` (17), `IllusionAndMinionTests`, `PhrogParasiteTests`, `MercPowerListTests`, `HeistGoldRewardTests`,
   `LethalHitHookTests`, `HeadbuttTests` each pin a game behaviour the old engine was made to match (turn-start kills after the
   roll, a Test Subject respawn, the merc's reinforcements, a giant killed by Thorns). A test fixture that binds a kernel with
   F08+F10 to every combat the tests build (an environment variable the `Fight` helper and `RunEngine` read) turns those into a
   switched-on regression suite for free. Where a test pins a known old deviation, the failure is the to-do list for R4 and the
   batches, measured instead of inferred.
4. **The two predicates agree.** In `EmuDump fuzz` with F10 on, assert at every step `CombatEngine.IsOverOrEnding(state) ==
   CombatEnd.IsOverOrEnding(k)`; before the holder handlers land, the expected disagreements are exactly the held-open corpses
   and nothing else.
5. **Caller scan.** Extend `construct commands` from writes to calls: every call of `DealDamageToEnemy`, `LandDamageOnEnemy`,
   `DealDamageToPlayer`, `LosePlayerHp`, `LoseHp`, `DealAttackDamage`, `AnswerDeaths*`, `HandleEnemyDeaths` in `Core/` is inside the
   else branch of a `Kernel.If` gate.
6. **N holders, one effect** (section 3.3): dispatch with two creatures holding the model equals one direct call of the old body.
7. **The move-end test** (1.3 C) and **the positional-loop test** (1.3 A, Oblivion) and **the target-index test** (1.3 B), each a
   three-enemy combat where the removed slot is not the last.
8. **Explained differences carry a value, not a field name.** Each `fuzz_explained.json` entry should name a minimal replay spec and
   the core2 value a rule test asserts, so the pattern cannot absorb a second, unintended difference in the same fields.

## 3. Risk and order

### 3.1 What first, what waits

First (before or with R4):
- The step-API acceptance test (3.2) and the switched-on run of the old suites (2.3 item 3). Both fail today; their failures are
  the specification of R4.
- R4 in two halves, each with the fuzzer and the traced set: (a) the card and potion damage entries with `Kill`, the removal, the
  positional-loop fix and the target-by-reference fix; (b) the enemy turn (`PerformMove` with the move-end bookkeeping settled),
  the win-check reroute and the F17 hand-off. The second half carries 1.3 C and the two-predicate seam.
- The handler batches in this order: the pilot (it proves the pattern), then the batches that hold *death* handlers (power-1 for
  Ravenous and Thorns, relic-1 for Gremlin Horn, power-2 for Surprise, power-4 for Infested and Heist, power-3 for Stock and Crab
  Rage) with the per-owner rule of 3.3 applied, then the LOCAL holders (Adaptable, Steam Eruption) so that the two predicates can
  agree; the pure fold batches (Strength, Vulnerable, Weak, the relic bonuses) are low-risk and can land at any time.
- The Fogmog reading (1.3 D), because the open-pair gate does not see it and switch-on with it open leaves an Act 1 fight unwinnable.
- Mechanism B's Lane B interim (Slow inside `BuffSystem.IncomingDamage` before its floor and cap): one site, one rule test
  (9 x 1.5 x 1.2 = 16, not 15), measurable on the lockstep, independent of the kernel. It changes the old engine's bytes, so it is
  its own commit under the corpus gate, not part of a kernel round.

Wait:
- The F06 order of AfterAttack relative to a card's next effect (Skittish, Gigantification): the plan rightly defers it; the
  fuzzer will list it.
- The HP commands (item 9), the monsters' pseudo-hooks, the F17 loss path: all need the decompile.
- Switch-on in `migrated_families.json` (R7): behind 0 open pairs *and* the Fogmog closer *and* the traced-set gate.
- The native run API accepting a kernel: after R7's measure, since without it the agent's self-play never runs the new order and the
  by-family gain is a referee-side number only.

### 3.2 The single test that most reduces the risk of landing wrong

A test through `CombatEngine.Step` (the old step API, as the lockstep drives it), with a kernel bound carrying F08+F10 and the real
`Registry` (not a test handler), on the migration plan's own traced setup: Ironclad A10, two Corpse Slugs with Ravenous, Strength 40,
Gremlin Horn held, a non-empty discard pile; the actions Defend, Defend, Headbutt on slug 0. Assert, at the stopped step with the
discard screen open: `state.Enemies` holds one creature; the survivor carries Strength +5 and Stunned 1 and announces Unknown;
the hand has one card more and energy one more than before the play (Gremlin Horn inside the kill, before the screen); the
`CommandLog.KillCalls` is 1; and after the answer the step finishes with the same result, HP and piles as the game trace. Then the
same fight with Twin Strike: one hit, `Hits == 1`. This is the only case with a game trace behind it, and it crosses every seam R4
adds: the reroute, the kill inside the hit, the removal before the screen, a power handler and a relic handler in the game's order,
the stop on `PendingSelection` and the replay on the answer. Today's `KillCommandTests` version of it drives the command, not the
step. Second choice, if only one more: the old suites under the switch (2.3 item 3), because it is nearly free and enumerates the
rest.

### 3.3 The cloud handler batches (CLOUD_BRIEFS.md)

Sound:
- Inert handlers (no switch flipped) keep every branch under the byte proof; landing commit by commit against the gates is right.
- The four tests per model (registered and not a stub; dispatch equals the old body; delete-mutant; absent with the switch off) are
  mechanical and catch a mis-registered hook, a wrong pass and a forgotten switch guard. The table test per batch stands in for the
  gate well enough.
- The stop rules (missing, private, inline, or signature mismatch: report, do not edit `Core/`) and the re-entry list are the right
  division between cloud and local.
- The decimal rule (the handler returns the addend or factor; the one cast stays in `CreatureCmd.Damage`) is correct and is the whole
  of mechanism B once Slow has a handler.

Not sound as written:
- **Per-listener dispatch of a body that acts on every holder.** `CombatEngine.Ravenous_AfterDeath` (line 4523) gives Strength and a
  Stun to *every* living enemy holding Ravenous in one call. The dispatcher calls the handler once per Ravenous instance (one per
  surviving holder); with N survivors each gets N applications. The brief's C2 names that function as Ravenous's body with no
  per-owner rule; the "one hook call per copy" rule is stated for Melancholy only. The rule must be general: an event handler acts
  for `c.Owner(self)` alone, and an old body that loops over holders is first split into a per-owner part the old loop calls too (the
  Melancholy recipe). `TryEnrageCrabPartner` looks idempotent (its comment says the rage is spent; read it), `Hex`, `Dampen`, `Constrict` are
  idempotent removals; Ravenous is not, and `TurnPlayerToFaceSurvivor` and the Surrounded pair should be read with the same question.
  The fourth test rule should add: two holders in the combat, one dispatch, the same state as one direct call.
- **"The condition the old call site has" is the wrong condition for a per-fallen body.** The old sites run inside `foreach (fallen
  in dead)`; a handler runs for a listener and receives the dead creature as an argument. The condition to carry is "the dead
  creature is my owner" for the powers of the dying creature (Surprise, Infested, Heist, Swipe, Possess, Stock, Steam Eruption,
  Adaptable, Reattach, Illusion) and "my owner survives" for the others (Ravenous, Crab Rage). The brief should say which, per row.
- **Test rule (2) proves equality with the old body, not with the game.** For the folds that is fine. For the event handlers the
  substantive gate is the LOCAL decompile review, and the brief says so; it should also require the N-holder case and, for a body
  that reads the roster (Ravenous, Crab Rage, Dampen), a dispatch while the dead creature is still listed (`MarkDying`), since that is
  the state the game's override sees.
- **The pilot's Hand Drill stop rule** is right; the pilot would be stronger with one event handler whose body does not loop
  (Melancholy after the per-copy split) so that the pattern for events is proven before power-1.
